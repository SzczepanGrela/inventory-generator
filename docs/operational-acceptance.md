# Inventory operational acceptance

These temporary tools prepare the remaining live acceptance gates. Their presence,
green CI and a normal release do **not** mark the exercises as performed.
Only dispatch from `main` during a coordinator/operator window with VPS monitoring
active. The workflow shares the `production` lock and protected environment with
normal deployment. Do not run direct Coolify promotions in parallel.

## Baseline and stop conditions

Record the actual current digest/revision from selected Docker inspect and public
health, container resource settings, UTC time, available host memory and the
neighbouring application's normal latency. Verify no pending deployment or other
agent is about to promote an image. Do not use a stale baseline copied from here.

Use the thresholds in [operator procedures](operator-procedures.md):
available RAM below 1000 MiB; host CPU above 85% for over 15 seconds or load average
above 3.5; TTT health latency above 500 ms or a 5xx; an actual OOM event; more than
three consecutive unexpected Inventory 502/503/504 responses. Stop generated
load immediately on a threshold or unreadable monitoring. Keep observation alive.
An interrupted/ambiguous deploy must be reconciled to a terminal state before
another deploy or restoration. Do not cancel a runner and assume that cancels
Coolify. Preserve existing databases, networks, proxy settings and other apps.

## Isolated unhealthy candidate

Prepare a disposable Coolify **Docker Image** application named exactly
`inventory-deployment-canary`, using the reviewed current Inventory image digest.
Do not clone production environment variables or secrets. Use an isolated app
network, port 8080 inside the container, **no domain**, **no host port mapping**,
no storage, preview deployments or pre/post-deployment commands. Make sure Coolify
has not autogenerated a domain. Apply 1 CPU, 512m memory and memory+swap, and
`--cap-drop=ALL --init`. Enable managed CMD health checking:

```text
curl --fail --silent --show-error --max-time 4 http://127.0.0.1:8080/api/health
```

Use interval/timeout/retries/start period `5/5/10/10`. Disable consistent container
names and connection to the predefined Docker network. Deploy the healthy baseline
first and verify its selected Docker inspect (including no mounts/host ports) and
health. Record its UUID and old container name. Capture Docker create/start/health/
kill/die/destroy/oom events restricted to this canary for the entire exercise.

Dispatch `acceptance.yml` with `mode=canary`, that app's UUID, healthy `digest` and
full image `revision`, and confirmation `isolated-canary-health-gate`. Leave the
previous-digest/revision fields empty. Both preflight and the private API guard
reject production as the canary target. The live guard also rejects domain, port,
storage, hooks and health/resource contract drift before changing anything.

The tool changes **only the canary's saved health command** to `/bin/false`, then
queues a replacement with the same immutable image. The running old container
retains its existing health command. It observes rejection for up to 180 seconds,
then restores the original saved health command and redeploys the healthy canary.
A timeout triggers cancellation with terminal-state confirmation; it is a failed
test, not a successful health-gate rejection. Unknown state or an ambiguous API
mutation stops further mutation and requires operator reconciliation. The job
prints only deployment IDs and status evidence, not raw API responses/logs/env.

Pass requires both workflow evidence of a failed candidate/healthy restoration
and operator Docker evidence that the old healthy container survived the failed
candidate. An early infrastructure/pull failure does not prove the health gate;
inspect the candidate's selected health state and Coolify failure reason. Keep
the canary for that readback, then remove only its identified resources. When
using the delete API explicitly disable `delete_volumes`, `docker_cleanup` and
`delete_connected_networks`; do not use global Docker prune. Record resource
absence separately from image retention. The stable image is also used by prod
and must remain available.

## Failed-smoke rollback on production

Choose a newly tested/attested Inventory digest with a different revision but
compatible application behaviour. For this closeout, tooling-only changes are
appropriate; do not use an old image that reverses the cache migration fixes.
If the main Quality workflow is waiting to promote that image, resolve that
pending job before starting the exercise; both use the same production lock.

Dispatch `acceptance.yml`, `mode=rollback`, candidate `digest`/`revision`, exact
`previous_digest`/`previous_revision` observed in production and confirmation
`restore-after-controlled-smoke-failure`. Leave `canary_uuid` empty. Preflight
verifies GitHub attestations and revision labels for **both** images. Production
baseline drift stops before mutation.

The harness calls the actual `coolify_release.deploy_release` path. Once the
candidate is healthy, its revision is stable and its real public exports/headers
pass, a dedicated callback deliberately raises a test failure. The ordinary
exception handler restores the saved digest. Normal deployments have no callback.
The harness passes only for its own injected failure followed by confirmed saved
digest, healthy app, stable old public revision and another full export smoke.
Genuine smoke errors, rollback errors and ambiguous API results remain failures.
This verifies response to a failed test; it does not simulate data loss or a host
outage. The app remains on the saved baseline after the drill.

## Rolling capacity and independent clients

Measure host resources, all old/new Inventory containers, real cgroup OOM counters,
export status/latency and public TTT usability over the same UTC window. An idle
overlap alone does not qualify aggregate capacity. Start with small exports, then
use only the locally qualified payloads and at most three active requests per
container. A coordinator-controlled direct local probe may be needed to address
both overlapping containers deterministically; never send forged client identity
headers to the public edge to manufacture capacity. Record the resulting scope.

Public client acceptance is separate: pair a bounded small-export burst from the
operator's VPS with requests from an independent public source during the same
interval. Record 200/429, Retry-After, body reason, CF-Ray, recovery and rejection
of attempted forwarded-header bypass. Two different Cloudflare locations prove
application-client separation, not per-IP edge isolation within one location.

Retire the temporary workflow, modules and injection hook after the dated evidence
is accepted. Keep ordinary release/rollback tests and the operator runbook.
